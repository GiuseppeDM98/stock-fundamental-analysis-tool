## 1. The output contract

### 1.1 Order and markers

- **Deep Value** (four requests since 2026-11-22, § 2.9): the web update searches and writes its notes after `<!--notes-->`; the valuation, with no tool, writes a short memo and then the JSON block as the LAST thing (`buildValuationSystemPrompt`); the report, in two halves, writes sections 1–5 and then 6–10 after `<!--report-->`, on numbers it is told are final. The server appends the stored JSON to the saved report as its last fence (`withResultFence`), so the numbers come first and the report argues them. Until then one request researched, wrote the report and closed it with the JSON (2026-10-29). **Lenses**: `<!--critique-->` and the critique in one request, then the final JSON alone in a request of its own (since 2026-11-20, § 3.2). Why (2026-10-29): the JSON restates numbers the report has already argued, so text and numbers stay coherent, and the stream is readable from the first heading instead of opening with a JSON blob.
- **The report reads its numbers as final, in the report's language** (2026-11-22, from the first real runs of the four requests and the owner's tour): `buildReportSystemPrompt` says that a scenario's `fairValue` is already the buy target, after the margin of safety, and that its intrinsic value is `bridge.intrinsicPerShare` (a run titled the buy target «Intrinsic Value» and took the margin off it a second time); and that the English heading template is translated into the report's language, keeping each `## N.` number and its order (an Italian run copied the English headings). Pinned by `__tests__/deep-value-prompts-contract.test.ts`.
- The markers are sentinels independent of language and section numbering: `REPORT_START_MARKER` / `CRITIQUE_START_MARKER` / `NOTES_START_MARKER` in `lib/report/parse-deep-value-json.ts`, interpolated into the prompts, so prompt, gate and strip share one source. They never reach the page: react-markdown 10 renders an HTML comment as visible text (`&lt;!--report--&gt;`, verified 2026-10-29), so the route's gate drops the marker and `stripJsonBlock` strips any repeat.
- The blind Phase 1 of a lens is unchanged: JSON first, then a short rationale; it is its own request and never streamed (§ 3.2).
- **The closing disclaimer is written in the report's language** (since 2026-11-09): the rule quotes the English text and asks for it "written in ${language}". Until then it was an English literal, so an Italian report or critique ended in English.
- **Older reports** (saved before 2026-10-29) carry the JSON at the TOP. `parseDeepValueJson` reads the LAST ` ```json ` fence, which in those reports is the only one, so both formats parse with no branch. The e2e seed keeps `e2e_an_panel` in the old format on purpose: it is the compatibility fixture.

### 1.2 The JSON block, field by field

Type `DeepValueResult` (`components/report/types.ts`); a lens adds `AnalystResult`'s fields. Nothing in it is trusted: `sanitizeDeepValueResult()` keeps only known keys with the right types.

### 1.3 Rules the code relies on

- **The MoS trap.** Stored `Analysis.fairValue{Bull,Base,Bear}` (and every `*FairValue*`) are **MoS-adjusted buy targets**: `intrinsic × (1 − mosPercent/100)`. The intrinsic value is NOT stored separately; reconstruct it with `grossUpToIntrinsic()` (`lib/report/valuation.ts`, never reimplemented): `intrinsic = stored / (1 − mosPercent/100)`. When `mosPercent = 0`, stored = intrinsic. The bridge's `intrinsicPerShare` is PRE-MoS, so `lib/grounding/postcheck.ts` grosses `fairValue` up before comparing: a direct comparison makes every check fail silently, always. It matters anywhere a value is shown or compared as "fair value": the exit signal threshold, `computeEvolution` (`lib/report/evolution.ts`), any label that says "Fair Value" vs "Buy Target".
- **The bridge rule** (`BRIDGE_RULE`, under every JSON template): the bridge always reads (multiple × driverValue − netDebt − minorities) / shares, or `intrinsicPerShare` directly when `multiple` is omitted. Equity-value methods (P/E, P/B, Residual Income, DDM, DCF on FCFE) declare `netDebt: 0` and `minorities: 0`; SOTP, NAV and EV/RAB give the summed enterprise value as `driverValue` with no multiple.
- **Narrow before dereferencing.** The parser returns `ParsedAnalystResult`, whose bull/base/bear may be missing: call `hasFullTriple()` first. A new run never saves an incomplete triple: the valuation phase fails and can be retried (since 2026-11-22, § 2.1). A row saved earlier with an incomplete triple has null fair values and no `resultJson`, and the panel shows `deepValueIncompleteJson` on it — never half a valuation. A malformed block still fails `JSON.parse` as a whole (§ 7, gotcha 29).
- **The server parses and stores.** The routes parse the model's text with the shared sanitizer and the store writes `JSON.stringify` of the result (§ 2.3): no client text is stored. Its key order is the sanitizer's.

## 2. Deep Value

### 2.1 The route — `/api/ai/deep-value`

- **Settings**: `resolveAiSettings()` (§ 6.2). When the request names no effort, the run goes at the user's default: no floor since 2026-11-20 (until then the higher of the default and `xhigh`), and nothing above `high` reaches the model (§ 6.1). An explicit effort in the request wins, also without a model: it then applies to the stored model (before 2026-10-29 an effort-only body was dropped; the Advisor route had the same drop).
- **One route, four phases**: the first request `{ ticker, language, mosPercent, datasetId, model?, effort?, thinking? }` creates the row and runs `update`; the chain then sends `{ analysisId, phase }` for `valuation`, `report1`, `report2`, and a Retry `{ analysisId }` alone (the server picks the phase, § 2.9). Each request claims the row at its phase (`claimRunPhase`), runs one runner of `lib/ai/deep-value-phases.ts`, writes its result and answers `done`.
- **Prompts, one per role**: `buildUpdateSystemPrompt`/`buildUpdateUserPrompt` (what is newer than the dataset, each fact with its source; never the price, never an analyst target), `buildValuationSystemPrompt`/`buildValuationUserPrompt` (Steps 1–4, the rigor block and the JSON template; dataset and web notes in, no tools), `buildReportSystemPrompt`/`buildReportUserPrompt`/`buildReportContinuationPrompt` (the ten sections on the FIXED VALUATION; the continuation asks for 6–10). `currentDate` is the run's `createdAt`, so every phase of one run states the same date. `dateClauseFor()` states today's date as the only source of "now" and derives the year from it (no hardcoded year: the model otherwise anchors to its training year). The analysis is **position-blind** (§ 2.6).
- **Stream gate**: `createStreamGate(marker)` (`lib/ai/stream-gate.ts`) buffers everything until the marker (`<!--notes-->` in `update`, `<!--report-->` in each report half), forwards only what follows, and handles a marker split across chunks. After the loop, `flush()` forwards the buffer if the marker never came and logs `[deep-value] <phase> marker never arrived; flushed`. The valuation streams nothing: its memo and JSON reach the page through the row.
- **`stop_reason`**: the valuation ends through `classifyValuationEnd` (no triple → failed, retryable, «no_valuation»; `max_tokens` → retryable; a refusal → not); a report half ends through `classifyRunEnd`, and `max_tokens` there is a retryable failure, not a truncated save. `max_tokens`: 16000 for `update` and each report half, 32000 for the valuation.
- **Run metadata on the row**: the route writes `aiModel`/`aiEffort`/`aiThinking` itself when it creates the row (§ 2.9); `aiThinking` is `buildThinkingParam(...).type !== "disabled"`, so Sonnet 5.5's `between_tools` (its "off" at every effort the app sends since 2026-11-20) records `true`; model and thinking are those resolved before the call, so a run answered by the Sonnet 5.5 refusal fallback still records `claude-sonnet-5-5` (the fallback note in the text names who answered). The `X-AI-Settings` header that carried them to the client's save is gone with the save (2026-10-27).
- **`maxDuration = 300`**, the Vercel Hobby ceiling, now per request: every model call is its own request (§ 2.9), and only a phase longer than 300 s is still cut. The figures that follow are of the single request before 2026-11-22. Measured cost of one run at `xhigh` without a dataset (2026-10-29, before the single path): 480k input + 45k output tokens and 26 searches, about $3.8; one lens on it about $2 (243k + 27k, 17 searches). On a web dataset (TRN.MI, 2026-11-09, from `/analyze`): the report 744 s, 552k + 51k tokens, about $4.2; the Skeptic blind-first 648 s (its blind card at 361 s). Per-phase durations: § 2.9.

### 2.2 The panel — `components/deep-value-panel.tsx`

- The only AI analysis mode: a violet panel on `/analyze`, for any global ticker, the report in one of 8 languages (`LANGUAGES`: English, Italiano, Español, Français, Deutsch, Português, 中文, 日本語), on the page's MoS. Its Decision Panel offers "Add to Watchlist" (a 409 reads "In Watchlist").
- The initial `aiSettings` are `DEFAULT_AI_SETTINGS` (`high`), so a Generate before `fetchAiSettings()` answers (or after it fails) runs at `high`; the fetched default replaces them as is. The user can change it in `<AiSettingsControl>`.
- **The chain** (`components/use-deep-value-run.ts`, since 2026-11-22): one click sends the first request, each `done` sends the next phase, and after `report2` the hook re-reads the row: the summary, the checks card and the recap read the row's `resultJson` and its `priceAtAnalysis`, the price the prompts saw, never the stream. A re-read that fails shows the streamed report and «Reload the page to see its numbers». While running, the panel lists the four phases (done, running with its seconds, waiting with «usually ~N min»: 2, 4, 2, 2); the web notes show in `<WebUpdateCard>` as soon as `update` ends, the report streams from `report1`. **`mosPercent` comes in as a prop** (it was once hardcoded to 0).
- **A lost stream is not always a lost phase**: the hook re-reads the row once; when it sits at the next phase with no request in flight (`deepValuePhaseWritten`) the chain goes on with no click and no error; otherwise the run is cut.
- The run's inputs (`DeepValueRunInputs`, `lib/report/deep-value-run.ts`: ticker, MoS, price, currency, language, dataset) are frozen at Generate, so a later change of the slider does not alter the run the checks card describes. There is no Save: the server wrote the row, and `done` carries its id, so the panel links «Open the saved report» (`/analyses/<id>`) next to the PDF.
- **Cut and Retry**: a stream that ends without a terminal event, or a read that rejects, is a cut: the panel shows the row as the server wrote it (its notes, the report part saved, `runError`) and what Retry will do (`retryPlanOf`: «Retry from: Valuation» within the hour, «Retry from the start, with a new quote» after it). Retry sends only `{ analysisId }`, enabled `RUN_RETRY_AFTER_MS` (330 s) after `runStartedAt`, with a countdown, and at once when no request is in flight (`runStartedAt` null); a 409 «dataset no longer available» turns it into «Run again» (a new run on a new dataset). `/analyze?ticker=X&resume=<id>` (the Retry link of `/analyses` and of the detail page) opens the panel in that cut state, and the run starts only from the click.

### 2.3 Persistence

- **Columns on `Analysis`**: `resultJson` (the sanitized final JSON), `currency`, `sector`, `reportLanguage`, `aiModel`, `aiEffort`, `aiThinking`, and per lens `reviewResultJson` / `optimistResultJson` / `qualityResultJson`; all nullable (migration `add_analysis_result_json`, additive, not repeatable: `ADD COLUMN` fails if the column exists). The scalar `fairValue*` and `valuationMethod` stay, and stay what consensus, ruler, watchlist and digest read.
- **Phase columns** (2026-11-22, migration `add_analysis_run_phases`): `runPhase` (the phase the row stands at: the one in flight, or the next to run; null once done), `updateNotesMd` (the web notes, in `SavedAnalysis` and the list select, out of the summary select) and `valuationMemo` (the valuation's reasoning, ≤ 4000 characters, read only by the report prompts: in neither select nor the type).
- **Written by the server** (`lib/analyses-store.ts`, server-only, since 2026-10-27): `claimRunPhase` takes the row for a phase with a conditional `updateMany` on `{ id, userId, runStatus, runStartedAt }` as read (a chain request only at the row's own phase with no request in flight; a Retry within the hour clears from the phase on, after it everything, the price included), stamps `runStartedAt` and steps a stored `aiEffort` down to `high`; `finishUpdatePhase` writes the notes, `finishValuationPhase` the memo, `resultJson` (only with a full triple: method truncated to 40, sector to 80, currency only when it is a 3-letter code) and the scalar `fairValue*`, `finishReportPart` the report, `done` and a null `runPhase` on the last; each clears `runStartedAt` and moves `runPhase` on. `failAnalysisRun` stores `runError` (≤ 300) and leaves what the phases wrote. Every finishing write is an `updateMany` on `{ id, userId, runStartedAt }`: a count of 0 means the row was deleted, or a newer run owns it, and the phase ends with «This analysis was deleted.» (not retryable). `POST /api/analyses` and `PATCH /api/analyses/[id]` are gone (405): no client writes an analysis.
- **Lens writes**: `saveLensBlind` writes the commitment (with its rationale and the quote Phase 1 worked on, § 3.2) and clears the lens's critique, fair values, method and result; `saveLensCritique` writes the critique and clears the five number fields (fair values, method, result); `saveLensResult` writes the numbers and `*ResultJson`, only on the row whose critique is still the one the request read (it is in the `where`: a count of 0 means another run replaced it, «This lens was run again elsewhere: reload the page.»). Each write clears what follows it, so the columns alone tell where a lens stands (`lib/report/lens-progress.ts`, § 3.2). The columns come from `ANALYST_COLUMNS`.
- **Selects** (`lib/analyses-select.ts`): `ANALYSIS_LIST_SELECT` lists every `SavedAnalysis` key, `as const satisfies Record<keyof SavedAnalysis, true>` — a key missing from either side breaks `npm run typecheck` (gotcha #20 is the silent version of this). `ANALYSIS_SUMMARY_SELECT` is the same minus the ten text blobs (report, the three critiques, the three blind and the three lens result JSONs) for the digest and other readers that only need numbers; the excluded fields come back `undefined` (not `""` or `null`), so a reader that needs `reportMd` — the last-fence fallback of a row without `resultJson` — queries it separately. `__tests__/analyses-contract.test.ts` pins both lists. **Mirror any new persisted field across all contract points**: the store (`lib/analyses-store.ts`), `types/analysis.ts`, `ANALYSIS_LIST_SELECT`, `ANALYST_COLUMNS` (`lib/report/consensus.ts`) for a lens column, the e2e seed.
- **`Analysis.datasetId` is in `SavedAnalysis` and the list select; `Analysis.groundingJson` is deliberately outside both**: legacy and read-only (§ 5.2), a blob the list never uses. The comment on the type says so; read it before "restoring" the field.

### 2.4 The saved detail page — `app/analyses/[id]/page.tsx` + `components/analysis-detail-body.tsx`

The server page reads the row and the open lots (aggregated into one position) and hands them to the client `<AnalysisDetailBody>`. A row with web notes shows them first, in `<WebUpdateCard>`: a `<details>` open on arrival, inside `.print-report`, its body printed even when closed: Chrome hides a closed body through `::details-content`, which a rule on the children does not reach, so the card opens itself on `beforeprint` and closes again on `afterprint`, with `app/print.css` for a browser that prints without the event (seen in a print preview, 2026-11-22). The summary (badges, cards, recap) comes from `resultJson` when the column is set, else from the last fence of `reportMd`; `hasFullTriple` decides whether the summary, the checks card and the analyst panel render at all (no triple → the banner and the plain Markdown body, no quote fetch). The body is `stripJsonBlock(reportMd)`. With an extract (`readAnalysisExtract`, § 5.2) the dataset tables follow the checks card, inside a `.print-report` wrapper (gotcha #27).

**One price per page.** `AnalysisDetailBody` resolves the price once — one `GET /api/quote/[ticker]`, else `priceAtAnalysis` in the result's currency, else none — and passes the same value to the position banner, the recap row, `<ValuationChecksCard>` and the analyst panel's gates. On the fallback each says so ("Price at analysis", "checks against the price at analysis (live quote unavailable)"); the banner shows a P&L only on a live price in the position's currency (`sameCurrency`), else a line saying why (`pnlUnavailable`); the fair-value cards and the recap show the distance from the price only on a price in the report's currency, else a note naming both (`recapCurrencyMismatch`); with no price at all a one-line note replaces the card. `priceAtAnalysis` is read in the currency of the quote it came from (`priceCurrency`, written with it since 2026-10-27; an older row without it is compared with nothing). A row whose run has not finished renders its status line instead (§ 2.9). Before 2026-10-29 the banner and the summary each fetched their own quote, and a failed one left the page with no card at all; the same day the cards still weighed a quote in pence against a report in pounds, off by 100.

### 2.5 Rendering a report — `components/report/*`

- **`<ReportBody markdown={...} />`** is the single place the `react-markdown` + `remark-gfm` + `prose prose-invert prose-report prose-sm max-w-none` recipe lives; don't hand-roll it in a component (it was once duplicated across three components with a violet/sky accent inconsistency). **`@tailwindcss/typography` is required** for any `prose*` class to do anything: without the plugin the classes are silent no-ops (gotcha #22). The custom variant `report` (`prose-report`, `tailwind.config.ts` → `theme.extend.typography.report`) adds a top rule and spacing on every `h2`, which gives the AI's `## N. Title` headings their section-divider look. Strip the JSON block (and the markers) with `stripJsonBlock()` before rendering any saved report — never a hand-written regex: the block is now at the end, and older reports have it at the top.
- **`<ReportShell>`**: the live panel and the saved detail page render the same layout: masthead (company/ticker/date) → `MethodBadges` → `FairValueCards` → `ReportBody` (inside a `.card`) → `RecapTable` → static disclaimer footer. Don't reintroduce a local `RecapTable`/`UpsideBadge`/inline card JSX in a new consumer. `RecapTable` uses the `.rtable` utility (AGENTS.md › Dense tables → cards below `sm`), so it collapses to cards on phones; its first `<td>` (scenario name) uses `.rcell-block` as the card title.
- **Print / PDF**: "Download PDF" calls `window.print()`, no PDF library. `app/print.css` (imported once in `app/layout.tsx`) scopes light-theme overrides to `.print-report` (the wrapper `<ReportShell>` renders); app chrome uses Tailwind's `print:hidden` in JSX. Upside/downside (emerald/red) and the violet accent are **kept** in print by product decision; only the neutral slate surfaces are inverted, via targeted selectors on the slate utility classes rather than a blanket `* { color: black }`. `break-inside: avoid` on cards, tables, paragraphs, list items and quotes, and `break-after: avoid` on `h2`–`h4` and on a paragraph followed by a table or a list (`p:has(+ table)`: its lead-in moves with the table, 2026-11-22), prevent mid-page splits; a block taller than a page still splits. The typography plugin's backticks around inline code are off for every `prose` block (`tailwind.config.ts`, DEFAULT variant: the lenses write gate names as code, 2026-11-22). Two traps: (1) a page hosting `<ReportShell>` must mark its OWN chrome `print:hidden` (`/analyze` printed its header, search and MoS as a first page until `analyze-client.tsx` did); (2) content OUTSIDE `.print-report` gets none of the overrides (gotcha #27): the analyst critiques are legible in print only because `ReportBody` carries its own `print:text-slate-900`. A sibling block meant for the PDF gets a conditional `print:hidden` (shown only with content) and keeps its controls `print:hidden`.

### 2.6 The valuation is always position-blind (hard invariant)

**Never inject the user's portfolio position (WAC, shares, P&L) or a prior estimate into the Deep Value or analyst prompts**; the run metadata (`aiSettings`, `language`) does not enter them either. The valuation's worth is its independence: anchoring it to what the user paid or to a previous run is motivated reasoning on a money decision, and it contaminates the saved report used for later comparison. A position-aware "Review Position (AI)" path existed and was removed for exactly this reason (July 2026); do not re-add a `reviewContext`/`prevFv`/`wac` field to `/api/ai/deep-value`. The two legitimate needs are met **outside** the valuation:

- **Hold / add / exit reasoning → the Advisor** (`/advisor`), which reads positions + saved analyses read-only and never emits a valuation.
- **Estimate evolution over time → a deterministic diff, not the AI.** `computeEvolution(prev, curr)` in `lib/report/evolution.ts` compares two saved analyses on the intrinsic scale (each grossed up with its own MoS), base scenario only; the consensus sub-row appears only when both saves carry analyst values. `computeEvolutionChain(analysesNewestFirst)` returns one `Evolution` per adjacent pair, so `EvolutionDiff` shows the whole save history. If a "how did X change" feature can be pure arithmetic over stored numbers, compute it — don't ask the model.

### 2.7 Reading a saved valuation — ruler, verdict, consensus

`ValuationRuler` / `ComparisonTable` / `axisFraction` / `Triple` live in `components/report/valuation-ruler.tsx`; `getVerdict` / `Verdict` / `VERDICT_BADGE` / `VERDICT_TEXT` in `lib/report/verdict.ts`; `grossUpToIntrinsic` in `lib/report/valuation.ts`. Extracted from `components/analyses-list.tsx` so `watchlist-client.tsx` could reuse the same ruler and consensus UI. **`/analyses` is the reference implementation — regression-test it after touching these modules.**

- **Zones encode the decision**: emerald buy (≤ buy target), amber watch (buy target → FV), neutral rich (≥ FV). `getVerdict(price, buyTargetBase, intrinsicBase)` → `buy | watch | over`, styled via the static `VERDICT_BADGE` / `VERDICT_TEXT` maps (never assemble class strings: AGENTS.md › Tailwind dynamic classes require static strings).
- **Signal-reliability flag** (`lib/report/signal.ts`, pure): `getSignalStrength(price, {bear,base,bull})` on the intrinsic scale returns `low | moderate | clear` — `low` when the base-vs-price edge is small relative to the bull↔bear cone (`signal/dispersion < ~0.15`). Both lists render a muted "weak signal" pill (`weakSignalLabel`/`weakSignalHint`) next to the verdict when `low`. Self-calibrating, pure arithmetic over the stored triple; it stops a fair-value ≈ price null result from reading as a confident call (§ 4, the design lesson).
- **Verdict and zones prefer the consensus** once an analyst lens has run: `buyTargetBase`/`fvEdge` (the `getVerdict` inputs and the zone props of `ValuationRuler`) come from `consensusTriple(a)`/`meanTriple(...)`, else from the base analysis. The base analysis's own tick (white) stays at its own value, so a disagreement is visible. **Change the zone props and `getVerdict`'s inputs together**, or the price dot sits in a zone that contradicts the badge.
- **One verdict basis**: `verdictBasis()` and `watchlistBuyTarget()` (`lib/report/latest-analysis.ts`) serve /analyses, watchlist, exit signal and digest alike; a latest save without values falls back to `latestAnalysisWithValues()`.
- **One price rule**: `comparablePrice(price, quoteCurrency, analysis)` (same file) passes the quote only in the analysis's currency (`sameCurrency`, § 5). On a mismatch there is no verdict, no price dot, no "Under FV" match, no exit signal (`getExitSignal`) and an `unknown` digest status (`digestPriceRead`), each with a note naming both currencies (`verdictCurrencyMismatch`; the email says it in Italian); an open position's P&L needs the price in the lots' own currency. Values are formatted in the analysis's currency, the price in its own. Added 2026-10-29: every one of these compared the raw quote, so a GBp quote against a GBP analysis read a hundredfold. `getQuote` turns a missing currency into `USD` (`lib/yahoo-client.ts`): a quote Yahoo returns without one is compared as dollars. The display has the opposite trap: `Intl.NumberFormat` accepts `GBp` as `GBP`, so a pence quote is written as pounds (`£7,000.00` for 7,000 pence; verified 2026-10-29, not fixed).
- **The axis stays on the intrinsic scale**; a `level` state (`"intrinsic" | "buyTarget"`, owned by the caller — `TickerGroup`, `WatchlistCard`) only moves marks and values, and `ComparisonTable` is controlled by the same `level` — don't reintroduce local toggle state.
- **Marks carry no inline value labels** (they collide when FV, lenses and consensus sit close): values live in a legend row under the bar (`● price · │ FV/Buy target · ╎ per analyst lens · ◆ consensus`). `markers.analysts` is `{key,label,value}[]`, one tick per lens that ran, colored via the static `ANALYST_TICK_BG` (skeptic slate, optimist fuchsia, quality indigo). Position a mark with `` `${pct}%` ``; a label that must stay inside the bar uses `left: clamp(16px, ${pct}%, calc(100% - 16px))`.
- **`currency?`** is optional: the watchlist passes the analysis's currency (the quote's when the analysis has none), `/analyses` doesn't.
- **Watchlist card** (`components/watchlist-client.tsx`, `WatchlistCard`): the same ruler and table, fed by `latestAnalyses: Record<string, SavedAnalysis>` (the latest saved analysis per ticker, consensus via `presentAnalysts`/`meanTriple`). **Its buy target uses the MoS of the watchlist item, not the analysis's**: the analysis (or the consensus) gives the intrinsic value, the item's `mosPercent` re-derives the buy target. **The verdict phrase names its source** — `belowBuyTargetPhrase`/`aboveBuyTargetPhrase` "(analysis)" vs the `…ConsensusPhrase` "(consensus)" keys, picked by whether a consensus exists, because the base buy target and the consensus can sit close but different (10.20 vs 10.10). The email digest mirrors it from `item.consensusBase !== null`.

### 2.9 Staged runs — one request per model call, written by the server

Since 2026-10-27 (after the staged «Consulente» run of net-worth-tracker) every AI call of a valuation is its own request, persisted by the server as it ends and retried from the phase it reached; the 300 s of Vercel Hobby then bind one phase, not a whole run.

- **The phases**: the Deep Value is four (`/api/ai/deep-value`: `update` — Sonnet 5.5 at `high`, the run's model on DeepSeek, at most `UPDATE_MAX_SEARCHES` = 8 searches, 10 rounds; `valuation` — the run's model, effort capped at `high`, no tools; `report1` and `report2` — no tools, 1 round each; since 2026-11-22); a lens is three (`/api/ai/deep-value/verify` with `phase: "blind"`, `"reconcile"` — the critique — and `"final"` — the numbers, since 2026-11-20, § 3.2). The research stage (§ 5.3) is three requests before the run (statements, market, estimates; since 2026-11-22), its partial state in a `ResearchRun` row, not in the analysis.
- **The row exists from the start**: `startAnalysisRun` creates it `running` at `runPhase: "update"` (empty report, `createdAt = runStartedAt = now`, the model settings, the price with `priceCurrency`) before the model is called, so `/analyses` shows «Running: Web update» while it works. `createdAt` is the run's start, `runStartedAt` only the request in flight (null between two phases). A retry reuses the row: the body is `{ analysisId }` alone (strict); within `RUN_RESUME_WINDOW_MS` (1 h) of `createdAt` it resumes from `runPhase`, after it it starts over from `update` with a new quote and a new `createdAt`; a resume from `update` on a row without a price reads the quote too. It answers 404 (not the user's), 409 «run already finished», «run still in progress» (inside 330 s), «phase out of order» or «dataset no longer available».
- **Events** (`lib/ai/sse.ts`, read by `lib/sse-reader.ts`): `stage { stage, analysisId?, runStartedAt? }` first (it also flushes the headers before a long model call), `text` for the streamed report or critique, then exactly one terminal event: `done { analysisId?, blind?, degraded? }` or `error { error, retryable }`. A stream that ends with neither is a cut (§ 2.2).
- **The server finishes the phase even if the client leaves**: `createSseChannel` ignores writes to a closed controller (an `enqueue` on a cancelled stream throws a `TypeError`: raised inside the text callback, it would carry a good run into the `catch`), and the row is written by the route, never by the page.
- **How a run ends** (`classifyRunEnd`, `lib/ai/run-outcome.ts`): an empty answer and `max_tokens` are failures the user can retry; a refusal is a failure that a retry would repeat; a turn out of search rounds with text is done with a note. A JSON without the full triple is a retryable failure: the valuation's («no_valuation», `classifyValuationEnd`, since 2026-11-22) and a lens's final request («no_numbers», since 2026-11-20); until then such a run was done without fair values, and its report still read.
- **Three clocks** (`lib/report/run-status.ts`): `RUN_RETRY_AFTER_MS` = 330 s — Retry is offered (and accepted by the server) only that long after `runStartedAt`, past the 300 s a live function can still be writing; `RUN_STALE_AFTER_MS` = 20 minutes — a row still `running` after that reads «interrupted» (the function was killed and nothing marked it failed); a row `running` with no request in flight reads interrupted at once; `RUN_RESUME_WINDOW_MS` = 1 h from `createdAt` — past it a quote and web notes are too old for a report dated then, and Retry starts over.
- **Readers skip unfinished rows**: `isDone` (`runStatus` null or `done`) on `/analyses`, the hub, the portfolio and the watchlist; `runStatus: "done"` in the digest's and the Advisor's `where`. Between two Deep Value phases a row is `running` with its numbers already written (after the valuation): a new reader must filter the same way, or it reads a valuation whose report does not exist yet. `/analyses` shows each unfinished row as a status line above its ticker's card, naming the phase («Running: Valuation», «Interrupted during: Valuation») and what Retry will do («Retry from: Valuation», «Retry from the start, with a new quote»; «Run again» without a dataset, Delete always); the detail page of one shows the same line, no report and no PDF.
- **What a kill does**: a function stopped mid-phase leaves the row `running` (Deep Value) or the lens without the phase it was in; the panel sees a cut, reads the row, and offers Retry from that phase. A Phase 2 retry reads the commitment from `*BlindJson`, a Phase 3 retry the critique too, so no phase is paid twice. A stream lost after the server wrote its phase is not a cut: the re-read row is exactly at the next phase (`lensPhaseWritten`), and the chain goes on with no click (2026-11-21); a row anywhere else is the previous run's, and the phase runs again. A kill runs no `finally`: the killed phase prints no `[ai-run]` line, and its duration is `runStartedAt` against the kill in the Vercel logs; `after()` runs in the same function and under the same ceiling, so it cannot write the failure either. Without Fluid compute the ceiling is 60 s (SETUP.md § Vercel Hobby).
- **Log**: one `[ai-run] <route> <phase> <ms> <model> <effort> <outcome>` line per request, beside the `[tool-loop] round N usage` lines.

## 3. The analyst panel

### 3.1 Pattern — multi-lens fresh-context verifiers

After a Deep Value analysis is **saved**, the detail page (`components/analyst-panel.tsx`) runs up to three independent second-opinion passes — **skeptic** (red team), **optimist** (constructive bull case), **quality** (long-term durability) — each streaming from `/api/ai/deep-value/verify` with an `angle` param (default `"skeptic"`).

- **One route, one parameterized builder**: `buildAnalystSystemPrompt(angle, …)` / `buildAnalystUserPrompt(angle, …)` share the JSON block, the authoritative-price guard and the MoS clause, and differ only in persona and focus (`ANGLE_CONFIG`). Rule of Three: three lenses → one builder + a registry, not three near-duplicate prompts. `AnalystAngle`/`ANALYST_ANGLES` are canonical in `types/analysis.ts`.
- **Shared structural checks**: `ANALYST_STRUCTURAL_CHECKS` is interpolated into all three lenses (EV→equity bridge completeness and minorities, method↔narrative coherence, same-basis comparables, scenario vs sensitivity, anchoring and MoS), because a real review found all three missing the same structural defects.
- **Non-prescriptive**: a lens commits to its own valuation and says whether the report's fair value should move, but issues no trade call more prescriptive than the report ("buy at €X" when the report concludes "hold").
- **Fresh context**: each lens is a distinct call that receives only the finished report (`stripJsonBlock`), not the original conversation; clean-context critique beats self-critique.
- **Each lens commits to its own valuation**: the critique after `<!--critique-->`, under `LENS_CRITIQUE_MAX_WORDS` (700) words and with no JSON, then its own bull/base/bear (same schema, MoS-adjusted: the MoS clause sits in the Phase-3 message, so it compares directly) in a final request that asks for the JSON alone. A lens block has `units` and a `bridge` per scenario but no `sensitivity` and no `dividends` (2026-10-11: a lens judges the report's number, it does not redo it, and three lenses would triple the cost; pinned by `__tests__/deep-value-prompts-contract.test.ts`). The route gates on `createStreamGate(CRITIQUE_START_MARKER)` in Phase 2 (the reconcile request, or the review that replaces it when Phase 1 degraded, § 3.2), with a flush + `[verify] critique marker never arrived` warning like the Deep Value's (§ 2.1) and, on `max_tokens`, an open JSON fence closed (`stripTrailingOpenJsonFence`) always before any route note (a note written inside the open fence was hidden with it, 2026-10-29); `__tests__/verify-route.test.ts` covers both. Effort: the user's default, capped at `high` per phase (`LENS_PHASE_EFFORT_CEILING`); the panel's initial state is `DEFAULT_AI_SETTINGS` (`high`). Search: at most `LENS_MAX_SEARCHES` (5) per request on Claude (§ 6.1).
- **Client state per slot**: `AnalystSlot` runs `useLensRun` (`components/use-lens-run.ts`), which sends the three phases as three requests and owns the state — idle, resumable (`from`: a commitment without a critique → reconcile, a critique without its numbers → final), running with its phase, failed (with `resumeFrom`), done. The initial state comes from the row through `lensPhaseOf`. It writes nothing: the route wrote the row, and after a retryable failure the hook re-reads it once (`fetchAnalysis`) and goes on when the phase was written (§ 2.9); a failure the route marks not retryable is final, with no re-read. «Retry phase N» (`lensRetryPhase`) sends that phase and what follows; «Run» starts from the blind phase. A resumed run keeps the blind card on screen, and Phase 3 the stored critique too. On demand only, one button per lens, never auto-run: each pass is three calls, the first two with web search. The live `/analyze` panel runs no review.
- **`max_tokens: 64000` + `stop_reason` tracking**: 16k truncated real critiques mid-word.
- **Authoritative price**: the route calls `getQuote(ticker)` (best-effort) and the system prompt marks the live price authoritative, so the lens does not "correct" it with a stale web quote.
- **The base report's gates reach every lens call**: `buildBaseGatesText` recomputes them (from `resultJson`, else the report's last fence; with the grounding extract when there is one) and `formatGatesForPrompt` appends them to Phase 2, reconcile or degraded review alike, so the lens addresses concrete FAILs. When the quote fails they are computed on `priceAtAnalysis` and the prompt says it is NOT the current price.
- **Persistence**: skeptic reuses the legacy `reviewMd`/`reviewFairValue*`/`reviewValuationMethod`; optimist and quality have `optimistCritiqueMd`/`optimistFairValue*`/`optimistValuationMethod` and the `quality…` equivalents; each lens also has `*BlindJson` and `*ResultJson`. `ANALYST_COLUMNS` (`lib/report/consensus.ts`) maps `angle` → columns (`critique`, `bull/base/bear`, `method`, `blind`, `result`), the single source shared with reads.
- **Consensus is N-way and centralized**: `lib/report/consensus.ts` (pure) — `consensusTriple(a)` / `meanTriple(triples)` / `presentAnalysts(a)` / `analystTriple(a, angle)` — the mean of the base analysis and every lens that ran; `null` when none ran (it would equal the base). It replaced `(base + reviewer) / 2` averages copy-pasted across four files. The disagreement Δ% is the same at intrinsic and buy-target level (MoS scales both). `Triple` lives in `lib/report/valuation.ts` (pure), re-exported from the ruler so server code can share it.
- **Adversarial Skeptic + no-praise rule**: the Skeptic's job is to BREAK the thesis — a **kill price** or an explicit statement that it can't build one. All lenses share an unconditional "do not praise" rule: (a) the errors, (b) the single most fragile assumption, (c) the one number that flips the conclusion; agreement is valid but never replaces (b)/(c). Distilled from a live review where all three lenses opened with "good work".

### 3.2 Blind-first in three requests (every lens) — `verify/route.ts`

Since 2026-11-09 every lens runs blind-first on the analysis's dataset: the route requires `analysisId` (400), answers 404 for an analysis that is not the user's, 400 «analysis has no dataset: re-run it with one» when the row has neither `datasetId` nor a legacy `groundingJson`, and 400 when that dataset cannot be read; all before any model call. The panel reads the same thing: `hasDataset` is `groundingExtract != null`, the extract the detail page read (`AnalysisDetailBody`; owner, 2026-11-09: the columns alone left Run enabled on a dataset that no longer validates, for the route's 400). Without it the panel disables Run with a hint, hides the model selector and keeps the saved lenses readable. `buildAnalystSystemPrompt` always describes the three phases: its single-phase variant, behind a `blindFirst` flag only the tests still set, was removed the same day.

When a model's opinion must be independent of a conclusion it will later read, run the SAME `system` prompt (it describes every phase up front) in separate requests: two since 2026-10-27 (§ 2.9; before, two turns of one request), three since 2026-11-20, when the critique and the final JSON in one request ran past 300 s:

1. **Phase 1 (blind)** — `phase: "blind"`, `buildAnalystBlindUserPrompt`: the data without `reportMd` (the absence IS the point). Nothing is streamed but the stage event; `max_tokens: 32000`. Its output order: JSON first, then a short rationale. `pickBlindCommitment` (`lib/ai/blind-commitment.ts`) takes the FIRST fence that parses with a full triple and the prose after it (≤ 2500 characters); the route sanitizes it and `saveLensBlind` stores it in `*BlindJson` with the rationale and `phase1Quote` — the live quote the phase was built on (`null` when the quote failed) — then `done { blind, degraded }` draws the blind card. The system prompt's closing rules are scoped per phase (disclaimer and nothing before `<!--critique-->` in Phase 2, the JSON as the whole answer in Phase 3): unscoped, they gave Phase 1 two opposite orders (2026-10-29).
2. **Phase 2 (reconcile)** — `phase: "reconcile"`, three messages, never Phase 1's transcript: the blind message rebuilt with the same arguments, an assistant turn of text only (`buildBlindAssistantTurn`: the commitment as a JSON fence without the rationale and the quote, then the rationale as prose — what the model itself produced, no thinking, no tool blocks), and the reconcile prompt. It echoes the blind numbers and states the rule that does the anti-anchoring work: a value may change ONLY by citing a fact or arithmetic error NOT available in Phase 1 — "the report argues X" is not a reason. Phase 2 writes `<!--critique-->` and the critique, under 700 words and with no JSON (a block written anyway is stripped); `saveLensCritique` stores it. A critique with no text writes nothing: an error to retry, not retryable after a refusal.
3. **Phase 3 (final)** — `phase: "final"`, 409 «run the critique first» on a row without a critique. Five messages: the three of Phase 2, the stored critique as an assistant turn (`buildCritiqueAssistantTurn`: the marker, then the critique), and `buildAnalystFinalUserPrompt` — the FINAL JSON alone, with `revisions` and the MoS clause; three messages after a degraded Phase 1. No tools and no cache (with no tools the prefix differs, so it would never read the first two requests' cache), one round, `max_tokens: 16000`, nothing streamed. Only a full triple is written (`saveLensResult`); a block without it, a round cap or `max_tokens` is «The final numbers did not arrive: retry.», a refusal is not retryable. A row with a critique and no numbers is the state «Phase 3 pending»: the panel opens on «Retry phase 3», `/analyses` puts a pill on the card (analisi-salvate.md), and the lens counts in no consensus until then.

**Phases 2 and 3 work on Phase 1's quote** (2026-11-20): the price is in the system prompt (the market-implied anchors) and in the blind message, so `prepareLens` reads `phase1Quote` from the column instead of a new quote; a price that moved between the two requests (a few cents in market hours) otherwise changed the prefix and the cache never served Phase 2. `parseBlindJson` reads the quote from the column only, never through the shared sanitizer: a model block cannot set the price a phase works on. A column without it (written before) reads the live quote. Verified (2026-11-20, Quality, Phase 2 with no search): `cache_read` 17,709 and `cache_creation` 2,334 — before the fix 0 and 29,213, the whole prompt rewritten.

**Degrade, never repeat Phase 1**: without a usable commitment (none parsed, or Phase 1 refused) the column is cleared and Phase 2 sends `buildAnalystUserPrompt` (the report, the dataset and the gates in one review, the critique alone) under the same system prompt, with a note; Phase 3 then follows on those messages, with empty `revisions`. `__tests__/verify-route.test.ts` covers it.

**What persists**: `*BlindJson` (the Phase-1 commitment) next to the final `*FairValue*` scalars, which remain what consensus, ruler, watchlist and digest read. The final JSON — `revisions[].reason` and the Skeptic's `killPrice` included — is stored in `*ResultJson` and read back on reload: the blind card shows the blind and final kill price, the cited revisions and the final `kill_price` gate; a lens with no blind commitment (a degraded Phase 1, or one saved without a dataset before 2026-11-09) gets `<AnalystFinalCard>` with the same fields and `FINAL_CARD_GATES` (kill price, scenario order, probabilities, cross-check, method family, horizon, bear vs price). The blind gate list drops `sensitivity_center` and `dividend_coverage`, which a lens block never declares (§ 3.1). During a live run only a full final triple feeds the card (`hasFullTriple`); a re-run that fails before its blind phase parsed restores the stored critique and result (an abort comes only from a newer run of the same lens, which owns the slot from then on).

## 4. Prompt rigor — `ANALYTICAL_RIGOR_BLOCK`

`buildValuationSystemPrompt` injects `ANALYTICAL_RIGOR_BLOCK` (module-level const, between the scenario step and the output step): **19 mandatory checks** distilled from real reviewer findings. Checks 1-12 (latest quarter; dated guidance only; guidance vs estimate; normalized EBITDA; scenarios reconciled to the stated sensitivity; base case re-derived at the base driver, not a stale TTM; same-basis comparables + anti-selection-bias + structural-discount test; complete EV→equity bridge with minorities, varied per scenario; method↔narrative coherence; **anchor the valuation lever to something independent of the price — the market-implied read is a control that reports the GAP, never the input**; MoS adequacy; internal-consistency linter) verify internal consistency. Checks 13-18 (unconditional) verify assumption validity, added after a live review (Iren S.p.A.) passed all twelve with a fatal basis mismatch: bear-case validity, bull/bear horizon symmetry, dividend coverage by FCF, ROIC-vs-WACC discipline, a mandatory structurally different second method with a numeric reconciliation, explicit probabilities. Check 19 (2026-10-29), sensitivity honesty: the 3×3 grid is recomputed, never interpolated, and its centre is the base intrinsic value. Checks are conditional where relevant, so they no-op where they don't apply.

The prompts are locked by the golden `__tests__/deep-value-prompts-golden.test.ts`: eight cases — (1) the valuation, (2) the valuation with a paste block, (3)–(6) the lenses (blind-first, Phase 1, Phase 2 with the gates, Phase 3), (7) the web update, (8) the report with its continuation (cases 1, 2, 7, 8 since 2026-11-22) — on one invented dataset, `__tests__/fixtures/dataset-fenicottero.ts`. It is regenerated only when a spec declares it, with `-u` and the diff read and reported; any other diff is a regression. It replaced on 2026-11-09 the golden of the prompts without a dataset (Quick mode), deleted with that path.

**Design lesson**: telling a model to "anchor X and cross-check against Y" can make it game the letter — an earlier version made the market-implied cross-check the anchor and produced base fair value ≈ price by construction. Prompt rules reduce this, never guarantee it; the structural cure is a deterministic anchor computed in code plus a post-check that recomputes the model's own bridge (§ 5.1, on every analysis; the dataset gates need a dataset, which every analysis has since 2026-11-09). The weak-signal flag (§ 2.7) is the other always-on read. The rule of the series since 2026-10: **the model declares, the code verifies**.

## 5. The financial dataset and the deterministic checks

**One path since 2026-11-09: every analysis starts from a financial dataset.** The flow on `/analyze`: dataset → preview → analysis. The dataset is researched from primary sources on the web (stage 1, § 5.3) or pasted as typed blocks (income statement, balance sheet, cash flow, historical multiples, forward estimates, peer comps), merged on the server when both exist, and saved as a `FinancialDataset` (§ 5.2); the user previews it with a source per row, confirms it, and Deep Value (stage 2) gets only its `datasetId`. Without a confirmed dataset Generate is disabled. Until then the paste was optional and a run without it (Quick mode) sourced everything by web search, the figures surviving only as prose. `lib/grounding/*` (pure) — `merge.ts`/`basis.ts`/`anchors.ts`/`reconcile.ts`/`postcheck.ts`/`prompt-format.ts`/`schema.ts` — computes historical multiple stats, a 3×3 valuation grid, the market-implied multiple (a **control**, never an input), basis reconciliation, gates and reconciliation warnings. Validated on two live runs with a paste (Iren S.p.A., Webuild/WBD.MI; July 2026).

- **Extraction is streaming, `max_tokens: 64000`** (`app/api/ai/grounding/extract/route.ts`): the API rejects non-streaming requests above a `max_tokens` threshold before generating, which once made every block fail at once; adaptive thinking counts toward the cap even on a transcription, and 16k let it truncate the JSON mid-object. Nothing is forwarded to the client. The model is pinned (Sonnet 5.5, medium effort) and ignores the stored default, with structured output (`extractionOutputFormat`); the Zod parse stays the boundary. The per-kind schemas live in `lib/ai/grounding-extract-schema.ts` (a Next route file may only export handlers), which lets a test keep the prompt example and the schema key-for-key identical.
- **Basis reconciliation (`lib/grounding/basis.ts`) — the highest-ROI piece.** The historical multiples (provider basis, P) and the pasted income statement (statement basis, S) need not share an EBITDA/EV definition. `computeBasisReconciliation(extract)` estimates `kE = EBITDA_P/EBITDA_S` and `kB = EVbridge_P/EVbridge_S` per year — direct from `marketCap`/`enterpriseValue` columns, else inferred from `evSales×revenue`/`pe×netIncome`/`pb×totalEquity` — aggregates to a median and returns `confidence: "high"|"low"|"unavailable"`. **Never silently assumes `kE=1`.** `toProviderBasis()` (a bare multiple) and `bridgeToProviderMultiple()` (equity value + statement-basis bridge, scaled by `effectiveKb` before dividing by kE) are the only doors into `percentileOf(...)` against the raw series. Injected FIRST in the anchors section, worded as binding ("computed in code — NOT your judgment").
- **The gates** run on every analysis, also on an older one saved without a dataset: § 5.1.
- **Injection split — system carries rules, user carries data.** Every builder requires `grounding` (since 2026-11-09). The system prompts carry `DATASET_RULES_BLOCK` — the dataset rules in the prompt: (1) web search rescoped to what the dataset cannot hold (anything after `meta.latestPeriodLabel`, qualitative context, restatements), never re-collecting a historical figure; (2) what must still be searched; (3) the dataset wins on history, unless a restatement published after its period; (4) forward estimates yes, analyst targets never; (5) one unit; (6) anchors are facts; (7) every peer in the table; (8) the basis reconciliation is binding; (9) raw text over transcription; (10) horizon; (11) an UNVERIFIED row lowers confidence and never alone supports the thesis; (12) the JSON's `units` equal `meta.units`. Each conflict goes into a "Data conflicts" note in the report. Rigor checks 4, 7 and 10 dropped their "when a block is provided" conditions. The user builders render the data via `formatGroundingForPrompt()`: raw blocks (base report only), the extract (with the research notes at its head, for the report and, since 2026-11-09, the lenses), ROW SOURCES (`formatRowSources`: one line per financials row and statement, then multiples, estimates and peers — `paste` or the host, `+ another source` when mixed, `UNVERIFIED`; never a block id), the anchors (led by the years of UNVERIFIED multiples they use), the warnings. Check the golden FIRST when touching these builders (§ 4).
- **Currency guard — `sameCurrency()` (`lib/grounding/currency.ts`).** Trimmed and case-sensitive (`GBp`, pence, is not `GBP`), empty or null never matches. `computeMarketImplied`/`computeImpliedExpectations` return `null`, not a wrong number, on a mismatch between the dataset (pasted or researched) and the quote, with a `currency_mismatch` warning: a research dataset reported in `GBP` against a `GBp` quote has no market-implied read; in `checkValuationBridges` a result whose currency differs from the quote's leaves every price gate "unavailable — currency mismatch" and `expectedValue` null. A price in one currency divided by an EBITDA in another is the worst bug class here; never remove the guard.
- **Lenses re-read grounding from the DB and get anchors, not the raw paste.** The verify route reads the extract, the dataset's stored warnings and its research notes (the ones the report reads, since 2026-11-09) by `analysisId` through `readAnalysisGrounding` (§ 5.2; never from the body: 100-200KB per lens) and calls `buildGroundingPromptContext(blocks=[], extract, ...)` — `blocks` empty on purpose, since the line-item detail would triple input cost over three passes. The base report's gates go to every lens call (§ 3.1).
- **The card**: `<ValuationChecksCard>` shows the checks under the report on the live panel and on the saved page, for every analysis; it is rendered as a sibling of `<ReportShell>`, hence gotcha #27.

### 5.1 Gates — every analysis, with or without a dataset

`checkValuationBridges(result, mosPercent, price, quoteCurrency, extract | null)` (`lib/grounding/postcheck.ts`) recomputes each scenario's bridge (arithmetic within 1%, MoS applied) and returns the gates in display order; `checkReportStructure(reportMd)` adds `sections_present`, appended by the card. The table lists all 17. Each gate is `pass` / `fail` / `unavailable`, and **a gate that cannot verify reads unavailable, never pass**. "No dataset" means no extract or one with no financial rows (`datasetOrNull`): the basis is `EMPTY_BASIS`, there is no market-implied multiple, and the dataset gates say "no dataset". The price is the one the page shows (§ 2.4). Intrinsic values are fair values grossed up by the MoS (§ 1.3).

| Gate | Reads | Rule | Unavailable when |
|---|---|---|---|
| `basis_same` | kE, base bridge multiple | pass: same basis, or the multiple within 5% of the same-basis median; fail: within 5% of the raw provider median only (the Iren signature) | no dataset, not an EV/EBITDA bridge, kE unknown, no base multiple, or it matches neither median |
| `horizon_consistent` | the three `driverYear`s | pass: all equal | a scenario without one |
| `bear_breaks_price` | bear intrinsic, price | pass: bear < price | currency mismatch, no bear or price |
| `multiple_vs_market` | base implied multiple vs market-implied, statement basis | fail: within 3% (the model copied the price) | no dataset, not an EV/EBITDA bridge, either multiple unavailable |
| `trailing_forward` | base `driverYear` vs latest FY, LTM-equivalent multiple | informs only, never fails: pass when trailing or when an LTM-equivalent percentile exists | no dataset, not an EV/EBITDA bridge, year missing, forward with no LTM equivalent |
| `netdebt_trajectory` | latest FY net debt, FCF, DPS × shares; bridges with `driverYear` = FY+1 | fail: a bridge's net debt below 95% of `netDebt − (FCF − dividends)` | no dataset, no bridge, an equity bridge (`equity bridge · net debt 0`) or an unknown method family, inputs missing, no scenario on FY+1 (` · long-horizon driver` when one is beyond) |
| `roic_vs_wacc` | `assumptions`, base multiple vs same-basis median | fail: ROIC < WACC with a multiple ≥ the median | no dataset, not an EV/EBITDA bridge, ROIC/WACC or multiple/median missing |
| `probabilities` | the three probabilities | pass: sum within 0.02 of 1 | any missing |
| `cross_check` | `crossCheck.intrinsicPerShare` vs base intrinsic | pass: delta ≤ 25% | no cross-check, no base |
| `cross_check_basis` | `crossCheck.bridge.multiple`, kE | `basis_same` on the cross-check's bridge (a DCF primary has no multiple: Webuild) | as `basis_same` on the cross-check's method and bridge, plus no cross-check |
| `scenario_order` | the three intrinsic values | pass: bear < base < bull, strictly | a scenario missing |
| `method_distinct` | method families of `method` and `crossCheck.method`, each anchored at the start of the name (`EV/EBITDA (peers)` is EV/EBITDA, `Peer EV/EBITDA` is none) | fail: same family (`EV/EBITDA` vs `EV/EBITDA (peers)`) | no cross-check, unknown family |
| `sensitivity_center` | the 3×3 grid, base bridge intrinsic | pass: centre within 1% of the base and the central row and column monotonic | no grid or no base bridge |
| `dividend_coverage` | year-1 base DPS × latest diluted shares vs mean of the last three reported FCFs (fewer when fewer are reported; the detail reads `mean FCF(Ny)`) | pass: a non-payer (`dividends: null`, before any data check) or ratio ≤ 1; fail: ratio > 1 or mean FCF ≤ 0 | no dataset, currency mismatch, path/FCF/shares missing |
| `units_match` | `units` vs the dataset's | fail: different | no dataset, either undeclared |
| `sections_present` | the report Markdown, `## N.` (also `．` or `)`) for N = 1…10 | fail lists the missing numbers | never |
| `kill_price` | lens `killPrice`, `killPriceNote` | pass: a number; fail: null without a note | null with a note (an honest "cannot build one"). Lenses only: present when the key is present, even `null` |

A fail on `basis_same`, `bear_breaks_price`, `roic_vs_wacc`, `scenario_order` or `sensitivity_center` shows red, any other fail amber. `trailing_forward` re-expresses a forward driver's multiple on the last reported EBITDA (`impliedMultipleLtm`/`impliedPercentileLtm`/`growthWedgePct`); `cross_check_basis` also enables `PostCheck.crossCheckBridge`, the cross-check's own arithmetic. `expectedValue` is display-only. **The EV/EBITDA gates read only an EV bridge on EBITDA** (`isEvOnEbitda`): an EV/EBITDA method, or a DCF on FCFF whose driver label names EBITDA. The pasted history, the basis reconciliation and the market-implied multiple are all EV/EBITDA, so `basis_same`, `multiple_vs_market`, `trailing_forward` and `roic_vs_wacc` read `not an EV/EBITDA bridge` on any other base bridge, `cross_check_basis` on any other cross-check bridge, and no implied multiple is computed for them; `netdebt_trajectory` needs an EV bridge of any kind. Before 2026-10-29 they read every bridge: a DDM cross-check on a per-share DPS yielded a meaningless implied multiple with a dataset (seen on a real Quick run). Without a dataset the card draws no implied multiple (nothing to rank it against), and the cross-check row only for its arithmetic. Every card names a gate through `GATE_LABEL_KEY` (`valuation-checks-card.tsx`); the codes are for the prompts and the tests (2026-10-29: the lens cards printed them; `__tests__/analyst-panel.test.tsx` asserts none reaches the screen). The lens lists drop the gates a lens block cannot pass (§ 3.2).

### 5.2 The financial dataset — `types/dataset.ts`, `lib/datasets/*`

- **One row per confirmed dataset** (`FinancialDataset`). A paste is born at "Analyze with this data", never at "Prepare data" (an abandoned paste leaves no row); a web dataset at the end of a research run (§ 5.3); a merged one from the two (§ 5.3). Columns: `userId`, `ticker` (normalized), `origin` (`paste` / `web` / `merged`), `currency`/`units`/`coverageLabel`, `dataJson` (the extract, rows and sources included, plus `datasetMeta`, which only the server writes; a paste's comes from the client validated by shape with `groundingPayloadSchema`), `blocksJson` (the paste: the raw text the Deep Value prompt reads, the lenses get none; null for web), `warningsJson`, `researchJson` (`ResearchMeta` of a web or merged dataset, null for a paste; a malformed one reads as `research: null` and the row stays). The merge itself never runs in the browser: the extraction route does it (below). `Analysis.datasetId` points to it (`ON DELETE SET NULL`: deleting an analysis keeps its dataset); the migration `add_financial_dataset` rebuilds `Analysis` (AGENTS.md § Prisma 7 + Turso). `groundingJson` is no longer written (since 2026-10-30; since 2026-10-27 only the server writes an analysis, and `startAnalysisRun` has no such field); older rows keep it. Only the warnings of the run that made the dataset are stored (`DATASET_WARNING_CODES` in `lib/datasets/parse.ts`: `block_extract_failed`, `value_conflict`, `meta_currency_conflict`, `meta_units_conflict`, and since the research `source_unverified`, `source_unknown_id`, `value_ignored_secondary`, `ebitda_derived`; `POST /api/datasets` and the research route drop the rest): every valuation recomputes the others from the extract and its own quote. The same list validates the read, and a stored warning outside it makes `parseStoredDataset` return null for the whole row: a writer that stores a new code widens the list first.
- **Provenance.** A financials row carries `sources`: one `DataSource` (`kind`, `url`, `title`, `asOf`, `blockId`, `verified`) per statement (`income`/`balance`/`cashFlow`, by `STATEMENT_FIELD_KIND`) plus a `mixed` flag per statement when a second block filled one of its fields; a multiples, estimates or peer row carries one `source`. A blob saved before parses with every source `null` and `mixed` false (the row schemas' defaults; `sources` defaults through a factory, since Zod 4's `.default(obj)` copies only the top level).
- **Merge at the server** (`mergeExtractedBlocks(results, blockOrder)`): the merge builds its own rows and never writes an input row (a row spread is shallow: a written `sources` would reach every row sharing it). It keeps the first value it sees, and the route sorts the results into `blockOrder` first (`orderByBlockOrder`), so the first block in the editor wins a field and the first block that fills any field of a statement owns it. A conflict names both blocks by kind and 1-based position among the blocks sent (`blockOrder`, empty blocks excluded): `revenue: 1000 (income_statement #1) vs 990 (income_statement #3)`. Nothing parses the detail.
- **Retry of one block.** The extraction request carries `blockOrder` (every block sent for the dataset, in editor order), the blocks to run and `priorResults` (validated); the route merges prior and fresh results in `blockOrder` (a block sent again replaces its earlier result, even when it fails again) and answers 502 only when no block has a result. A failure reads `<kind> #<position>` (written and read only in `lib/grounding-warnings.ts`; the editor shows, and the dataset stores, the position in its own list, empty blocks counted), so even a lens prompt, which gets no blocks, names the statement. The editor also re-sends any block with no result that did not fail (added or edited since), or the merge would silently miss it, and rebuilds the warning of every failed block it did not re-send: the route only knows this request's failures, and until 2026-10-30 a retry that fixed one of two failed blocks dropped the other's warning from the preview and from the saved dataset (`__tests__/grounding-input.test.tsx`). After a retry the saved blocks are the editor's current non-empty blocks.
- **Routes**: `POST /api/datasets` (paste: 201 `{ id }`; merged: 201 with the preview bundle, § 5.3; `web` is a 400), `GET /api/datasets/latest?ticker=&maxAgeDays=` (204 when none), `GET /api/datasets/[id]` (404 for another user's; its client helper `fetchDataset` has no caller yet, the e2e authorization pair uses the route). `lib/datasets/store.ts` (server-only) scopes every read to the user; `parseStoredDataset` (`lib/datasets/parse.ts`, pure) returns `null` on any malformed column.
- **One reader**: `readAnalysisExtract(userId, analysis)` — the dataset by `datasetId`, else the legacy `groundingJson` through `parseStoredExtract` — for the detail page; `readAnalysisGrounding` adds the stored warnings and the research notes, for the verify route. The Deep Value POST requires `datasetId` (400 `datasetId is required` / `dataset not found` / `dataset ticker mismatch`) and rebuilds the context from the row (blocks, extract, stored warnings deduplicated by `code|fiscalYear|detail`, the research notes); its tool loop runs at `GROUNDED_MAX_TOOL_ITERATIONS` (12), the rescoped search needing far fewer rounds than the 35 of a run that collected everything. A Retry (`{ analysisId }`) reads the dataset from the row, scoped to the user, and answers 409 «dataset no longer available» when it is gone (§ 2.9). The extract JSON in the prompt skips `sources`, `source` and `datasetMeta`: the provenance reaches the model as the ROW SOURCES section (§ 5), by host, the same `sourceHost()` the chips use.
- **UI.** `<DatasetSection>` on `/analyze` looks up the user's latest dataset of the last `DATASET_REUSE_MAX_AGE_DAYS` (7) days, aborting and checking the ticker so a late answer for the previous one is dropped. The section, «Financial dataset», always opens once the lookup answers. With a dataset (used or not: one saved for a run that then failed is offered too), it shows its date and origin (`paste`, `web`, `web + paste`), `<DatasetTables compact>` (last three years), its stored warnings (plus the currency against the quote), "Use this dataset" (no AI call), "Refresh data" (a new research; on a merged or paste dataset the paste is merged again into the new web one) and "Edit the pasted data" (the editor, seeded with the dataset's blocks unless the local draft differs from them, text included: an unsaved draft wins and is announced, `chooseStartingBlocks`) or "Add pasted data" when it has none. Without one: "Search the web for the data" and "Add pasted data", nothing starts by itself (a research costs and takes minutes). During a research a counter in seconds; a failure shows «Research failed — <the route's message>» with "Retry the research" and "Add pasted data" (a missing provider key is the route's 503); a dataset that was in view before the failed refresh comes back on reload (owner, 2026-11-09). The preview of a web or merged dataset lists the sources the research cited without opening them, and offers "Analyze with this data →" (confirms it, no AI call), "Refresh data" (a new research, merged again with the merged dataset's paste or with the one whose merge failed) and "Add pasted data" on a web dataset, "Edit the pasted data" on a merged one (the paste's stored blocks, or the local draft for the paste just confirmed; the new confirm merges with the same web dataset) (owner, 2026-11-09). Starting a research or a merge clears the confirmed dataset (the merge since 2026-11-09: before, the previous one stayed confirmed while the merge was previewed); a merge that fails after a successful research keeps the web preview, with the error; one that fails after a paste keeps the editor open, with the error and nothing confirmed. A paste confirmed while a web dataset is in view is merged on the server (`createMergedDataset`), else saved alone; its confirm button waits for the merge (`onConfirm` is awaited: a second click once saved a second paste and a second merge, 2026-11-09). The EV-columns hint (`showPasteHint`) shows on the paste editor's own preview only. A late answer for a previous ticker is dropped. Reuse lives only here, one click after a look at the numbers. `<GroundingInput>` (`components/grounding-input.tsx`) is the editor (typed blocks, 40k characters each and 200k in total — `GROUNDING_MAX_BLOCK_CHARS` / `GROUNDING_MAX_TOTAL_CHARS`, `types/grounding.ts` —, a per-ticker draft in `sfa:grounding:<ticker>`; source-agnostic: any provider's tables): "Analyze with this data" saves the dataset and hands `{ id, extract }` up. `<DatasetTables>` (one table each for income, balance sheet, cash flow, multiples and estimates, shown only when it has a value, nothing at all when none has; years in columns, the first row "Source" with a `<SourceChip>` per year: 📋 paste, 🌐 host, unverified, +1, —; no peer table: peers show in the preview's aggregates) shows in the preview, the reuse view and the saved page.

### 5.3 Research (stage 1) — `app/api/ai/research`, `lib/ai/research-*.ts`, `lib/datasets/merge-sources.ts`

Without a paste, the financials used to come from the web inside the valuation run and survived only as prose. The research stage collects them first, as data with a source on every row, and saves them as a `FinancialDataset` with `origin: "web"` (2026-10-30). Since 2026-11-09 `/analyze` runs it from `<DatasetSection>` (§ 5.2) through `useResearchRun(ticker)` (`components/use-research-run.ts`, over `startResearch` / `continueResearch` / `readResearchState`; no override: it follows the global default) and posts the merge through `createMergedDataset(ticker, pasteDatasetId, webDatasetId)` (`lib/dataset-client.ts`).

- **The run, in three parts** (2026-11-22; one request until then, 245–668 s, past Vercel's 300 s): statements → market (multiples and peers) → estimates, each its own request with its own caps, saved as it ends in one `ResearchRun` row (`lib/datasets/research-run-store.ts`; a column per part holding `{ status: "done", output, seenUrls, searches, fetches, durationMs, servedBy }` or `{ status: "skipped" }`). `POST /api/ai/research { ticker, aiSettings? }` reads the quote (name, exchange, trading currency; never the price, position-blind), resolves the model (`researchAiSettings`: Sonnet 5.5 `high` when the provider is Anthropic, whatever Claude model the default names; the user's DeepSeek model at `high` on DeepSeek; the override lives only in the body, and only its model counts), drops the user's runs older than 24 hours, creates the run and does the statements; `POST { runId, part, skip? }` (strict: a body with both a ticker and a run id is a 400) does the next part, `GET ?runId=` answers `{ runId, next }`. The part a run expects is the first without a record (`nextResearchPart`, `lib/ai/research-parts.ts`): another part is a 409 with `next` in the body, a run not the user's or gone a 404, a skip of the statements a 400 (they are the dataset; market and estimates are optional). Each part is one `runStreamWithToolLoop` call, nothing streamed, `max_tokens: 32000`, adaptive thinking, `high`, top-level `cache_control` on Anthropic, `maxIterations` = its searches + fetches + 1, `{ fetchBudget }` = its fetches; its user prompt names what the statements declared (currency, units, fiscal year end, latest period, years). A part's error answers its own 502 with `runId` and `part`; a market part that finds nothing is `done` with its note. The part that completes the run closes it (`combineResearchParts`): saves the dataset, reads it back, re-reads the quote best-effort (a failure leaves the market-implied read out, not the dataset), deletes the run and answers `{ next: null, result }`; a close that failed after the third record is repeated by the same POST without a model call. «Continue without» records a `skipped` part: the dataset gets an empty section and a `research_part_skipped` info warning naming it, shown in the preview. `ResearchMeta` sums the parts and lists them in `parts` (absent on rows researched in one request); `model` is the resolved model, `servedBy` the one that answered through the Sonnet 5.5 refusal fallback. Missing provider key → 503 «research requires the Anthropic/DeepSeek API key». Log: one `[research] <ticker> <part> <model> <ms>ms stop= cap= searches= fetches= seenUrls= blocksByCaller=` line per part, `[research] <ticker> <part> skipped` for a skip, `[research] <ticker> <part> error <status>: <message>` for a thrown error.
- **The client** (`components/use-research-run.ts`): one click runs the chain; `<DatasetSection>` shows three rows (○ ● ✓ ✕, the running one with its seconds and each with its usual minutes) and, on a failure, Retry (the failed part only) and, on market or estimates, «Continue without». A lost answer (a fetch that rejects, a body that is not JSON) reads `GET ?runId=`: a run already past the part goes on with no click (at most 3 times a chain), a run still at it is a failure with Retry, a 404 makes Retry a new research. A ticker change stops the chain before its next request. Nothing resumes a research once its tab is closed.
- **Tools** (`buildResearchTools(model, budget)`, `lib/ai/client.ts`; the caps in `RESEARCH_PART_BUDGET`): statements 10 searches / 5 fetches, market 9 / 2, estimates 6 / 1. Claude gets `web_search_20260209` and `web_fetch_20260209` (`max_content_tokens: 40000`, which does not limit a PDF: the statements' prompt allows two, `RESEARCH_MAX_PDFS`, the others none), both with `max_uses` from the budget and `allowed_callers: ["direct"]`: called from code execution, `max_uses` re-armed at every `pause_turn` resume (16 fetches under a cap of 8 on 2026-11-20); called directly it counts the whole turn, and dynamic filtering is off, so pages enter the context whole. Never declare `code_execution` next to them. DeepSeek gets `CUSTOM_WEB_SEARCH_TOOL` and `CUSTOM_WEB_FETCH_TOOL` (`lib/ai/web-search-tool.ts`, DeepSeek's Fetch API: `# title` + Markdown cut at 60,000 characters with a closing line; every failure, the budget refusal included, starts with `FETCH FAILED`); its searches are bound by the rounds, its fetches by `fetchBudget`. The loop runs a turn's searches in parallel (the Search API allows 5 requests per second per account; a 429 reaches the model as a `tool_result` and no log prints it: serializing them waits for one to be seen, 2026-10-30) and its fetches one at a time (per-domain QPS); only an executed fetch spends the budget, one past it gets the budget message («(N in this step)»), and a route without `fetchBudget` (Advisor, earnings, valuation) answers any `web_fetch` with it, never a throw.
- **The contract** (`lib/ai/research-prompt.ts`, `lib/ai/research-schema.ts`), one per part on a shared text (`buildResearchSystemPrompt({ currentDate, part })`): the statements return `meta`, `sources`, `financials` (`statementsPartSchema`), the market part `notes`, `sources`, `multiples`, `peers`, the estimates `notes`, `sources`, `estimates`; market and estimates are told not to fetch a PDF, and the estimates collect the published ones only. Primary sources first (IR press releases, then filings, data providers only for multiples), no target prices, five fiscal years (three at least), `fiscalYear` = the year the fiscal year ENDS, units and reporting currency declared once, `sources` (≤ 30, `id` ≤ 10) with `sourceIds` per statement on financials rows and one `sourceId` on the others, a short log, then the JSON fence LAST, read with `lastJsonFence` (`lib/report/parse-deep-value-json.ts`, the valuation's own reader). Each part's example and its schema are pinned key for key (`__tests__/research-contract.test.ts`); the model's `meta` is `researchOutputMetaSchema`, apart from `researchMetaSchema` (`lib/datasets/parse.ts`), which reads the stored `ResearchMeta`. The preprocess drops a bad source entry (URL not absolute http(s), id not 1-10 characters) instead of failing the run — its rows read as `source_unknown_id` —, keeps the first entry of a repeated id, maps an unknown `kind` to `other`, nulls a free-text `asOf`, keeps 30 sources and drops financials rows with no figure; a missing nullable field reads null, free text is clipped. 502s: invalid JSON, or an answer whose every source entry the preprocess drops («Research returned an invalid dataset»: `sources` needs one), no financial rows on the statements («No financial data found»), iteration cap, `max_tokens`, refusal, a turn that ended on `tool_use`.
- **Verification** (`collectSeenUrls`, `lib/ai/transcript-urls.ts`): a cited URL is not an opened URL. Each part stores the URLs its transcript opened, and a source verifies against those of the whole run (a page the statements opened verifies a multiple citing it); each part resolves its ids against its own `sources` list, never a merged one (two parts may both call a page `pr25`), and an unverified URL two parts cite is warned once. A source is `verified` only when its normalized URL (origin + path, no query, no trailing slash, host lowercase) appears in a search or fetch RESULT of the transcript: `web_search_tool_result` / `web_fetch_tool_result` on Claude, the `tool_result` of a client `web_search` (its URL lines) or of a `web_fetch` that read a page on DeepSeek. Error blocks add nothing; a domain alone is not enough. A row whose sources are all unverified is kept (chip «unverified», `source_unverified` naming the URL, the URL in `ResearchMeta.unverifiedSources`); only sources a row cites count, an uncited entry of `sources` changes nothing. `blocksByCaller` counts the result blocks by type and `caller.type`: with dynamic filtering a search or fetch can run from code execution, and a URL seen only in code-execution output would read as unverified.
- **To a dataset** (`researchToDataset`, `lib/ai/research-to-dataset.ts`): ids resolve to web `DataSource`s (a fresh copy per row), every series sorted by ascending year (anchors and gates read the last element), two rows of one year fused field by field (`value_conflict` above 1%; a statement the second row fills from another URL is marked `mixed`, chip "+1"), an unknown id warned once per year, peer tickers normalized, `meta.notes` into `ResearchMeta.notes`. **EBITDA the company does not publish is computed here, never by the model** (owner, 2026-10-30, after real runs on ENI and Coca-Cola found no group EBITDA): `ebitda = ebit + depreciationAmortization` on every row with EBIT and D&A and no EBITDA, named in one `ebitda_derived` info warning (the years); when D&A comes from another page than EBIT the income chip says "+1". `depreciationAmortization` is a cash-flow field of every financials row (`STATEMENT_FIELD_KIND`), stored as a positive amount whatever sign the page used (until 2026-10-30's fix a cost line printed negative was stored negative; only the sum took its absolute value), null on pastes (no extraction schema asks for it) and on datasets saved before (schema default). ## 6. AI settings and the Anthropic integration

### 6.1 Anthropic integration

- **Model split** (route fallbacks; the user's stored default or a per-run override wins): `claude-opus-4-8` for Deep Value and the analyst lenses (`max_tokens: 64000`; the user's effort, `high` at most, § 2.1), `claude-sonnet-5-5` for the Advisor (`max_tokens: 16000`, `high`) and the earnings lookup (`medium`).
- **Thinking** from `buildThinkingParam()` (`lib/ai/client.ts`): `{ type: "adaptive" }` while the user's toggle is on (default); off → `{ type: "disabled" }` on Opus 4.8 / Sonnet 5 and `{ type: "between_tools" }` on Sonnet 5.5 (accepted at `high` or below, the only levels the app sends since 2026-11-20).
- **No effort above `high`** (2026-11-20): `xhigh` and `max` ran requests past 300 s for little gain, so the catalog offers `low`/`medium`/`high` on Claude and `low`/`high` on DeepSeek; `AI_EFFORT_LEVELS` keeps all five so an older stored `xhigh`/`max` is still recognised, and `callSiteDefaultEffort` steps it down to `high` (§ 6.2). A phase may cap lower (`capEffort`, `LENS_PHASE_EFFORT_CEILING`: `high` in each lens phase today).
- **Search cap per lens request** (2026-11-20): `buildWebSearchTools(model, { maxUses: LENS_MAX_SEARCHES })` sends `max_uses: 5` with `allowed_callers: ["direct"]`, the same definition in `blind` and `reconcile` (one prefix for the cache; a whole lens: 10 at most). `max_uses` counts a whole turn, `pause_turn` resumes included: «Searches from earlier requests in that turn count against the limit, unless Claude ran them from code execution» (Anthropic docs, «Web search tool», § Max uses, read 2026-11-21). The `_20260209` tool calls from code execution by default, so without `direct` the cap re-armed at every resume; with it dynamic filtering is off and results enter the context whole. The count across a resume is the documentation's word, not yet a measurement: the paid probe of 2026-11-22 (Sonnet 5.5, `max_uses: 3`, a prompt asking 15 searches) used 3 searches in one response and never paused, so it did not exercise a resume; the research's real runs did not exercise one either (no part paused in five attempts, 2026-11-22, § 5.3). On DeepSeek the search is the client's tool and the bound is the rounds (`RECONCILE_MAX_TOOL_ITERATIONS`, `GROUNDED_MAX_TOOL_ITERATIONS`), not the searches (owner, 2026-11-21). The research stage has its own caps per part (`RESEARCH_PART_BUDGET`, § 5.3); the Advisor and the earnings lookup carry none. Each `[tool-loop] round` line ends with `searches=N fetches=M`: `usage.server_tool_use` on Claude, the client's `tool_use` blocks on DeepSeek.
- **`"xhigh"` and `between_tools` are typed by the SDK** since the bump to `^0.133` (2026-10-12): `buildEffortConfig()`/`buildThinkingParam()` pass them with no cast. Don't add a cast for a value the SDK doesn't type yet: bump the SDK.
- **Sonnet 5.5 rejects non-default sampling params** (`temperature`, `top_p`, `top_k` → 400).
- **Web search**: `{ type: "web_search_20260209", name: "web_search" }` (dynamic filtering, current models); `web_search_20250305` for older ones.
- **Streaming**: `runStreamWithToolLoop()` (§ 6.2), `content_block_delta` + `text_delta`; `client.beta.messages.stream()` on Sonnet 5.5 for the refusal fallback.
- **`max_tokens` must budget thinking + web-search reasoning**, not just the visible answer: the Advisor at 4096 stopped mid-word on long Discovery replies (now 16000). It is a ceiling, not a target.
- **Surface `stop_reason: "max_tokens"` — never truncate silently.** Track it from `message_delta` and enqueue a visible note before closing; the verify route also closes an open JSON fence first (§ 3.1); a Deep Value phase cut by `max_tokens` is a retryable failure instead, never a truncated save (§ 2.1, since 2026-11-22).

Streaming routes append a "declined" note; JSON routes answer a specific error. Branch on `stop_reason`, never on `stop_details` (can be `null`). A refused blind Phase 1 degrades to a review without the blind commitment (§ 3.2); Phase 2 never carries Phase 1's transcript, refused or not.
- **Server-side refusal fallback on Sonnet 5.5** (2026-10-12): every `claude-sonnet-5-5` call goes through `client.beta.messages` with `betas: ["server-side-fallback-2026-07-01"]` + `fallbacks: "default"` (`usesServerSideFallback()`, applied inside `lib/ai/tool-loop.ts`). Not sent to Opus 4.8 / Sonnet 5 (no fallback for them), never to DeepSeek (no beta surface on its Anthropic-compat endpoint), Claude API only (Bedrock/Vertex/Foundry would need the SDK's client-side middleware). ## 7. Gotchas (numbered as in AGENTS.md)

13. **Claude non-streaming multi-text blocks.** With `client.messages.create()` and `web_search`, `content` often holds several `text` blocks: early reasoning between tool calls, the final JSON in the last one. `response.content.find(b => b.type === "text")` returns the **first** (wrong). Concatenate all text blocks and match on the joined string:
    ```typescript
    const allText = response.content
      .filter(b => b.type === "text")
      .map(b => (b as { type: "text"; text: string }).text)
      .join("\n");
    const match = allText.match(/```json\n([\s\S]*?)\n```/);
    ```
25. **A provider's server-side tool call can leak raw internal syntax into a text stream** if its Anthropic-compat translation fails to parse it. Reproduced in production with DeepSeek's server-side `web_search`, non-deterministically (`<｜DSML｜tool_calls>...` in visible chat text). Routes that gate pre-report text (Deep Value, verify) are shielded; routes that stream raw text (Advisor) are not. Fix: declare a standard function-calling tool and execute it yourself (`lib/ai/tool-loop.ts` + `lib/ai/web-search-tool.ts`). A spike that runs clean once or twice proves nothing for a route with no gate.
26. **A tool loop with no "marker never reached" failsafe fails silently.** Deep Value once buffered everything until its marker; when the DeepSeek loop hit `maxIterations` first, the stream closed with zero bytes and the client set `status: "done"` — no error anywhere. Three fixes together: size `maxIterations` to the route's research depth; always `flush()` the gate when the marker never came (both routes, with a `console.warn`); and decide the outcome on the server (`classifyRunEnd`, § 2.9): an empty answer is a failed run, retryable, written on the row and sent as an `error` event — never a `done`. A stream with no terminal event at all is a cut, and the panel reads the row instead of guessing.
27. **A component rendered as a sibling of `<ReportShell>`, not inside it, gets no print-safe styling.** `app/print.css` scopes its overrides to `.print-report`; `<ValuationChecksCard>` sits outside it and reads darker in the PDF (a visual defect only manual testing catches). Nest a new post-report component inside `.print-report`, or give it explicit `print:` variants matching `print.css`.
28. **`runCreateWithToolLoop` reports `hitIterationCap`, resumes `pause_turn` and logs usage per round**, like its streaming sibling; it returns `{ message, stopReason, hitIterationCap, messages, servedBy }`. Before that, a loop out of rounds mid-`web_search` returned the last `tool_use` message as an answer and `/api/earnings` answered a generic `502 "AI returned no parseable result"` (production, 2026-08-24, DeepSeek). The route now answers a specific 502 ("ran out of web search rounds") and runs on `DEEP_RESEARCH_MAX_TOOL_ITERATIONS`.
29. **The parser returns `ParsedAnalystResult`: narrow with `hasFullTriple()` before any dereference** (§ 1.3). bull/base/bear may be missing; an incomplete triple shows `deepValueIncompleteJson` and saves null fair values and no `resultJson`. **Deep Value JSON parse is all-or-nothing** (moved from CLAUDE.md § Known Issues on 2026-11-21): one malformed nested field in the model's closing JSON block (the last ` ```json ` fence) discards the whole bull/base/bear/method via `JSON.parse`; the saved page still renders the report, but without the valuation summary.
